# P0 — Fundação (Studio Carol Lucas Experience + Studio OS) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up the Next.js/Supabase/Drizzle foundation (repo, tooling, design tokens, auth, RBAC/RLS, observability, CI) so that Epic 1 (core schemas) and Epic 2/3 (Admin/Portal UI) can be built on a stable, deployable base.

**Architecture:** Single Next.js (App Router, TypeScript strict) monolith deployed to Vercel, backed by Supabase Postgres via Drizzle ORM, Supabase Auth for both passwordless client login and staff email/password login, RBAC enforced server-side via a shared `lib/auth/rbac.ts` helper plus Postgres RLS. No microservices. Route groups (`(site)`, `(client)`, `admin`) separate the three product environments inside one app, sharing the same backend/data source per PRD §4.

**Tech Stack:** Next.js (stable/LTS) + React + TypeScript strict + App Router · Tailwind CSS + CSS variable design tokens · Supabase (Postgres + Auth) · Drizzle ORM + drizzle-kit · Zod · Vitest · ESLint + Prettier · Sentry (`@sentry/nextjs`) · GitHub Actions CI · Vercel deploy.

This plan covers **Epic 0 — Fundação** from `docs/TASKS.md`: SCL-001, SCL-002, SCL-009, SCL-004, SCL-005, SCL-006, SCL-007, SCL-008, SCL-003 (SCL-010 — creating `docs/TASKS.md` itself — is folded into Task 1). Epic 1 (Client/Lead/ExperiencePackage/Shoot/Payment schemas) is the **next** plan, built once this one is merged.

## Global Constraints

- Next.js in a stable/LTS release, React, **TypeScript strict mode**, App Router, Server Components by default where appropriate. (PRD §10.1)
- Tailwind CSS with CSS-variable design tokens matching prototype V2.3; shadcn/ui preferred for admin components; public site keeps its own editorial direction, not generic SaaS look. (PRD §10.2)
- Supabase Postgres + Drizzle ORM; migrations versioned in the repo; Zod for input validation. (PRD §10.3)
- Supabase Auth; passwordless (magic link or OTP) for clients; email+password for staff/admin now, architecture ready for MFA later; RBAC; RLS on client-accessible data. (PRD §10.4, §5.3)
- **Never expose the Supabase service role key to the browser.** (PRD §12)
- Authorization must be validated server-side and at the data layer — hiding UI is not access control. (PRD §3.6)
- Sentry for errors, structured logs for critical operations. (PRD §10.8)
- Domain is registered at Hostinger; deploy target is Vercel with PR preview deployments. (PRD §10.7)
- TypeScript strict, automated lint/format, tests for business rules; no important financial rule lives only in the frontend. (PRD §14)
- Commit messages must include the Task ID, e.g. `SCL-001: init repo`; branches follow `feat/SCL-123-slug`. (PRD §19.8–19.9)
- Never edit/renumber a migration that has already been merged. (PRD §19.7)
- No secrets committed; `.env.example` documents variable names only.

```tsx
  variant?: "ink" | "outline";

    "inline-flex items-center justify-center gap-3 font-sans text-[10px] tracking-[0.2em] uppercase px-7 py-4 transition-colors duration-300 cursor-pointer";

    outline: "bg-transparent text-ink border border-line hover:border-ink",
  };

  return <button className={`${base} ${variants[variant]} ${className}`} {...props} />;
}
```

```ts
import { cookies } from "next/headers";
import { createServerClient } from "@supabase/ssr";

export async function createSupabaseServerClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            );
          } catch {
            // Called from a Server Component render — session refresh happens in middleware (Task 6) instead.
          }
        },
      },
    }
  );
}
```

- [ ] **Step 3: Implement `lib/auth/session.ts`**

```ts
import { createSupabaseServerClient } from "@/lib/supabase/server";
import { db } from "@/db/client";
import { profiles } from "@/db/schema";
import { eq } from "drizzle-orm";

export type Role = "admin" | "staff" | "client";

export type CurrentUser = {
  id: string;
  email: string;
  role: Role;
};

export function resolveRole(profile: { role: Role } | null): Role {
  return profile?.role ?? "client";
}

export async function getCurrentUser(): Promise<CurrentUser | null> {
  const supabase = await createSupabaseServerClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();

  if (!user || !user.email) {
    return null;
  }

  const [profile] = await db
    .select({ role: profiles.role })
    .from(profiles)
    .where(eq(profiles.id, user.id))
    .limit(1);

  return {
    id: user.id,
    email: user.email,
    role: resolveRole(profile ?? null),
  };
}
```

- [ ] **Step 5: Implement session-refresh + route-protection middleware**

Create `middleware.ts` at the repo root:

```ts
import { NextResponse, type NextRequest } from "next/server";
import { createServerClient } from "@supabase/ssr";

export async function middleware(request: NextRequest) {
  let response = NextResponse.next({ request });

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value));
          response = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) =>
            response.cookies.set(name, value, options)
          );
        },
      },
    }
  );

  const {
    data: { user },
  } = await supabase.auth.getUser();

  const path = request.nextUrl.pathname;
  const isAdminRoute = path.startsWith("/admin") && !path.startsWith("/admin/login");
  const isClientRoute = path.startsWith("/minha-experiencia");

  if ((isAdminRoute || isClientRoute) && !user) {
    const loginPath = isAdminRoute ? "/admin/login" : "/login";
    const redirectUrl = new URL(loginPath, request.url);
    redirectUrl.searchParams.set("redirect", path);
    return NextResponse.redirect(redirectUrl);
  }

  return response;
}

export const config = {
  matcher: ["/admin/:path*", "/minha-experiencia/:path*"],
};
```

Note: `/minha-experiencia` is the real client-portal path referenced by the matcher; the placeholder `app/(client)/page.tsx` from Task 3 will move under that path in SCL-301 (Task 3's route-group page was only a build smoke test, not the final route).

- [ ] **Step 3: Implement `lib/auth/rbac.ts`**

```ts
import type { CurrentUser, Role } from "@/lib/auth/session";

const ROLE_RANK: Record<Role, number> = {
  client: 0,
  staff: 1,
  admin: 2,
};

export function hasMinimumRole(role: Role, minimum: Role): boolean {
  return ROLE_RANK[role] >= ROLE_RANK[minimum];
}

export function requireRole(user: CurrentUser | null, minimum: Role): CurrentUser {
  if (!user || !hasMinimumRole(user.role, minimum)) {
    throw new Error(`Forbidden: requires role >= ${minimum}`);
  }
  return user;
}
```

- [ ] **Step 5: Add row-level security to `profiles`**

RLS policies aren't part of Drizzle's schema DSL, so this is a hand-written SQL migration applied the same way as generated ones. First check the next sequence number:

```powershell

```

Create `db/migrations/0001_profiles_rls.sql` (adjust the number to whatever comes after the file Task 5 generated):

```sql
alter table "profiles" enable row level security;

create policy "profiles_select_own"
  on "profiles" for select
  using (auth.uid() = id);

create policy "profiles_update_own"
  on "profiles" for update
  using (auth.uid() = id);

create policy "profiles_admin_full_access"
  on "profiles" for all
  using (
    exists (
      select 1 from "profiles" p
      where p.id = auth.uid() and p.role = 'admin'
    )
  );
```

This is the pattern every future client-data table (`clients`, `shoots`, `payments`, ...) reuses in Epic 1: enable RLS, `select`/`update own`, and an admin-bypass `exists` subquery against `profiles`.

```ts
type LogLevel = "debug" | "info" | "warn" | "error";
type LogContext = Record<string, unknown>;

function log(level: LogLevel, message: string, context?: LogContext) {
  const entry = {
    level,
    message,
    timestamp: new Date().toISOString(),
    ...context,
  };
  const line = JSON.stringify(entry);

  if (level === "error") {
    console.error(line);
  } else if (level === "warn") {
    console.warn(line);
  } else {
    console.log(line);
  }
}

export const logger = {
  debug: (message: string, context?: LogContext) => log("debug", message, context),
  info: (message: string, context?: LogContext) => log("info", message, context),
  warn: (message: string, context?: LogContext) => log("warn", message, context),
  error: (message: string, context?: LogContext) => log("error", message, context),
};
```
